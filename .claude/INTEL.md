# INTEL — Lessons Learned

Every agent reads this at startup and applies these lessons. Append a new entry whenever you learn a
durable lesson or make a mistake worth never repeating.

<!-- Format: - **[Category]**: mistake → what to do instead -->

- **[CI Gate]**: `checks` and `e2e-gen` are STRICT required checks on `dev` and `main`. Never bypass them. Run `npm run check` and `npm run e2e:gen` locally and confirm green before opening a PR.
- **[Merge Gate]**: `dev`/`main` require one human approval. Agents OPEN PRs (`gh pr create`) and STOP — never run `gh pr merge`. The human (CEO) approves and merges.
- **[TDD]**: Wrote implementation before the test → ALWAYS Red-Green-Refactor. Write the failing test first, watch it fail for the right reason, then write the minimum code to pass.
- **[Requirements Fidelity]**: Reworded a user's issue and changed its meaning (CF-001/CF-008) → copy user-provided statements verbatim when asked, and verify exact polarity/decision text before creating or editing issues.
- **[Scope Control]**: Logged issues for out-of-scope / unimplemented areas → only record issues for currently implemented scope unless the human explicitly asks for forward-looking backlog items.
- **[Requirement Drift]**: Kept an old assumption after the human changed direction → treat the latest human directive as the source of truth and update the issue/plan text immediately.
- **[Shell Safety]**: A scripted interactive prompt appeared to hang → prefer deterministic non-interactive reproduction; the CLI is promptless in non-TTY (`NO_INSTALL=1` + env vars like `PROJECT_TYPE`, `VITEST_PRESET`).
- **[Test Execution]**: Parallel Vitest runs with coverage raced on `coverage/.tmp` → run Vitest sequentially (or in one invocation) when coverage outputs share a temp dir.
- **[Spellcheck]**: New committed docs / agent files reddened the `checks` gate → add new vocabulary to `cspell.json` (it scans `**/*.{js,mjs,cjs,md,json,yml}` and commit messages) before committing.
- **[Spellcheck/cspell tokenization]**: A template literal `\n\n<lowercase-word>` in source (e.g. `readme.js`) glues the `\n`'s trailing `n` to the word → a bogus token (the `n` from `\n` joined to `oxlint`) that whitelisting the real word will NOT fix. The rendered output is fine (real newlines). Split the source string (concatenation) to break the token — never whitelist the fake glued word. Capitalized words (`\n\nBiome`) dodge this via cspell's camelCase splitter.
- **[Branch staleness]**: A feature branch's config can drift behind `dev` (this branch's `cspell.json` lacked `oxlint/oxfmt/Groq/ECONNREFUSED`; `npm run check` doesn't even exist as a script here or on dev — the gate is the 5 commands run individually). Before assuming a red gate is your change, diff config against `origin/dev` (`git show origin/dev:cspell.json`). Local `npm run spellcheck` scans ALL on-disk tracked files incl. planning docs (`TODO.md`, `docs/superpowers/*`).
- **[TDD/false-green RED]**: A new RED test that asserts a short bare substring passed with NO implementation. Root cause: the test fixture's project name embedded that substring (the generated README echoes the project name in its heading), and the companion assertion was already true for every project of that class. A RED that passes is not a RED. Assert a distinctive artifact (a specific filename) AND the ABSENCE of the thing being replaced, and always confirm the RED fails for the intended reason before writing code.
- **[Spellcheck/SDD docs]**: The full local `npm run spellcheck` scanned committed SDD design docs under `docs/superpowers/` and reddened the gate on prose tokens (a matrix label; a backslash-n glue artifact, see the tokenization note above) unrelated to the code change. Fix applied: `docs/superpowers/` is now in cspell `ignorePaths` (like `scripts/`) — internal design artifacts are not spellchecked. Before assuming a spellcheck red is yours, diff the offending file + `cspell.json` against the branch point (`git diff <base>..HEAD -- cspell.json <doc>`); an empty diff means it is pre-existing.
- **[Spec fidelity / defaults]**: A task brief asserted `runCli(tmpDir)` is "default oxlint", but the default linter is `eslint` — `src/prompts/common.js` only accepts `LINTER` of `biome`/`oxlint`, else `eslint`. The RED test then failed on the wrong assertion. Verify default answers against `src/prompts/` before encoding them in a test; pass the non-default explicitly (`LINTER=oxlint`) when that is what you mean.
- **[ESLint template deps]**: A project type whose `eslint.config.js` imports React plugins (`eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`, `globals`) must add those to that type's devDeps gated on `linter === 'eslint'`. The base eslint block in `src/utils/install.js` does NOT include them (only the `frontend` block does), so otherwise the type ships a config that fails to load. Integration tests run `NO_INSTALL=1`, so a missing runtime dep is invisible to them — validate the dep list by hand.
- **[Spec fidelity / default injection]**: A brief's linter-default snippet routed the fallback through `undefined` (`['biome','oxlint'].includes(LINTER) ? LINTER : undefined`) then `linter = electron ? 'oxlint' : 'eslint'` — which silently clobbers an explicit `LINTER=eslint` (not in the includes-list, so it falls to `undefined` → forced to the type default). When a default-injection funnels "everything else" through one path, put every explicitly-valid value (here `'eslint'`) in the accept-list, and pin it with an "honors explicit override" test asserting the overridden artifact is present (`LINTER=eslint` → `eslint.config.js` exists). Provided snippets are hints, not gospel — verify the override paths.
- **[Vitest coverage provider]**: A shipped `vitest.config.ts` with `coverage: { enabled: true }` makes EVERY `vitest --run` (incl. the `native` preset) load `@vitest/coverage-v8`; if it isn't installed, `check`'s test step fails. `install.js` only adds the provider for the `coverage` preset generically, so a type that ships that config (frontend, and now electron) must push `@vitest/coverage-v8@^2` for `native` too (frontend already does). A brief's dep snippet may omit it — cross-check the config's `coverage.enabled` against the installed provider. `NO_INSTALL` integration tests can't catch this; only `e2e:verify` (real install + check) does.
- **[E2E gen manifest / conditional files]**: `scripts/e2e/matrix.mjs` `expectedFiles(combo)` is type-based (static `MANIFESTS`). Files that are conditional on an env toggle (electron ships renderer vitest files only with a preset; playwright files only with `PLAYWRIGHT=1`) must NOT go in the static MANIFEST — that would force every combo of the type to ship them and fail the no-toggle baseline. Make `expectedFiles` env-aware instead (push the files when `combo.env.VITEST_PRESET`/`PLAYWRIGHT` requests them). Frontend sidesteps this only because it ships its vitest files unconditionally.
- **[Playwright testMatch vs `.e2e.ts`]**: Playwright's default `testMatch` is `**/*.@(spec|test).?(c|m)[jt]s?(x)`, so a spec named `app.e2e.ts` is NOT auto-discovered — `npx playwright test` finds zero tests. It's invisible to gates because the live `_electron` run is display-gated and never part of `check` (verify only installs/typechecks/builds the playwright scaffold), so confirm discovery by hand with `npx playwright test --list` on a real scaffold. Resolved (CF-049): the electron `playwright.config.ts` sets `testMatch: '**/*.e2e.ts'` — keep it as long as specs use the `.e2e.ts` suffix (chosen to stay distinct from Vitest's `.test`/`.spec` files, which Vitest's `include` matches and Playwright's would too).
